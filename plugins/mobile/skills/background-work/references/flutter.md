# Flutter background work

## Core location
Dart itself can be the core. Express queue behaviour, retry timing and status calls as a single pure unit with no framework imports and no plugins. Hand it the clock and any OS state as arguments. One set of unit tests covers it. Platform code then just hosts the OS hooks. Note the choice in a decision.

Go native instead (`shared-core`) in two cases: the job must run while no Flutter engine is loaded, or it must behave identically to a native-only build.

## What to use for what
Examples use a notes app.

- **Deferrable or periodic sync.** The usual pick is `workmanager`, which sits on WorkManager (Android) and BGTaskScheduler (iOS).
  - It invokes a top-level Dart function inside a separate background isolate.
  - That isolate sees none of the UI isolate's memory, and none of its providers. Recreate what the task needs inside the callback, open the database there, and return quickly.
- **Uploads the user began, or large files.** Hand the transfer to the OS: user-initiated jobs or a foreground service on Android, a background `URLSession` on iOS. Reach it through a plugin like `background_downloader` or a thin platform channel. Upload from a file on disk. Use the client id to link each result to its record.
- **Continuous, visible work.** On Android a foreground-service plugin; on iOS the matching background mode. Both must be justified at store review.
- **Calling native code.** Go through platform channels, preferably generated by `pigeon`. Keep bridge types inside the data layer.

## Rules
- Isolates keep separate memory. They meet only in the database (Drift gives each isolate its own connection, or use `DriftIsolate`) and in the queue's lease row.
- Annotate the background callback with `@pragma('vm:entry-point')`. A release build otherwise tree-shakes it out.
- Check every plugin's docs before you call it from the background isolate. Not all of them work there.
- Unit-test the Dart task body like any function, using fakes (`write-tests` in `check`). Real devices prove that scheduling and survival work (`device-test`).
- On iOS nothing says when `BGTaskScheduler` work will run. Add a foreground path for anything a user is waiting on.
