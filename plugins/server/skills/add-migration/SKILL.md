# Add migration

Change the schema as described by `$ARGUMENTS`. If it is empty, ask what gets stored, who reads it, and the expected row count.

**Run on:** opus at high. A careless migration can freeze production or wipe data, and both are hard to reverse.

## Use it when
- You create or alter a table, column, index or constraint.
- You backfill, or enforce uniqueness over rows already in the table.

**Not for:** questions that only read data (`server:db-check`).

## Before you start
Read `AGENTS.md` and the conventions, then learn:
- the migration tool and how to call it;
- the home of entities and mappings;
- how a local database is started;
- when migrations ship: ahead of new code, as a job, or by hand.

The stack file under `references/` in `server:server-rules` lists the exact commands and the concurrent-index caveat. Look at recent migrations for naming and style. Next, size: how many production rows sit in each table you touch? Millions of rows, or hot writes, make a table large, and every rule below gets stricter. Missing a fact? Ask once and offer to record it in `AGENTS.md`.

**Stop if:** the tool, the deploy order or the list of large tables is unknown.

## Steps
1. **Design the change.**
   - Put the entity where the project's recorded choice says. A single table does not justify a new layer.
   - Use UUID keys, zoned timestamps in UTC, short-text enums, and units in column names.
   - Apply the constraint list in `server:server-rules` step 14: `NOT NULL`, foreign keys that say what happens on delete, unique indexes, `CHECK` ranges.
   - Each filter, join and sort in the new queries needs an index. Where only live rows matter, make it a partial index.
   - Make each row a member can read reachable via its tenant id.
   - Spatial columns declare one reference system and carry a spatial index when filtered. Time-series tables are partitioned by time, indexed on `(owner_id, time DESC)`, and have a retention rule.
   - Decide what happens to these rows when an account is deleted.
2. **Cut it into expand, migrate, contract.** While a deploy rolls out, live servers and released clients still use the old shape.
   - Expand: add nullable columns or new tables, and have the code write to both shapes.
   - Migrate: move the data in a batched job, outside the migration.
   - Contract: a later change makes the column required or removes the old one, once no reader is left.

   Renames and drops never happen in one go. Say in the PR which step you are on.
   **Stop if:** the next step is not written down in an issue or a PR note.
3. **Create the migration** in the project's usual way: generated by the data layer (then print the SQL for this migration alone) or hand-written as versioned SQL. You must read the final SQL in both cases. Use raw SQL where the tool falls short, for example partitioning or concurrent index builds. Those typically cannot run inside a transaction.
4. **Read the SQL.** Rework the migration if a large table meets any of these:
   - it gets rewritten, by a column type change, by `NOT NULL` added over existing rows with no default, or by a non-constant default;
   - an index is built without the concurrent option;
   - an `ALTER` grabs a lock, for instance a constraint added without first marking it not valid and validating separately;
   - data is backfilled inside the migration;
   - a column or table is dropped or renamed while running code still reads it;
   - there is no down path and no stated reason to roll forward.

   Give the migration session a lock timeout. Then a blocked migration fails fast and does not hold up all traffic behind it.
   **Stop if:** for any statement you cannot say which lock it takes and how long it holds it on the largest table.
5. **Apply and verify locally.**
   1. Boot the local database, run the project's migrate command, then the full test suite.
   2. Exercise the down path (or documented rollback) once and go up again. No down path? State the roll-forward fix, and test the migration against a fresh database.
   3. Run `server:db-check`: every table, column, constraint and index is there, new queries hit the indexes, and row counts before and after a backfill match the cohort.
   4. Run the integration tests for the new data on this database.
6. **Adding a uniqueness rule over existing rows.** Duplicates make a unique constraint fail, or it is added "not valid" and the duplicates stay hidden. Work in this order:
   1. Count duplicates. Agree a repair rule with the owner: keep the oldest, merge, or flag.
   2. Run the repair as a reviewed, batched job, never in the migration. Recount until zero.
   3. Build the unique index online (concurrently, outside a transaction if required).
   4. Attach the constraint on top of that index, and make the code map a violation to a conflict result.
   5. Test two things: inserting the duplicate now gives the expected result, and repaired rows match the agreement.
7. **Write the PR.** It carries the SQL (or a summary), your lock and rewrite findings, the current and next of expand, migrate and contract, the backfill plan, retention and deletion, and the rollback (`ship:deploy-check`).

## Done when
- [ ] The migration is exactly one of expand, migrate or contract, and the following step is written down.
- [ ] For the largest table, every statement has its lock and duration stated.
- [ ] Migration, rollback and the full suite pass locally (commands and output shown).
- [ ] The PR includes the `server:db-check` results.

## Never
- Never modify a migration once any shared environment has run it. Add another.
- Never backfill within a migration on a big table.
- Never combine drop or rename into one step while code or clients still use the old shape.
- Never run a destructive change on a shared environment without the user's clear OK.
